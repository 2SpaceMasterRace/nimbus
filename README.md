A clean, provider-agnostic Python interface for cloud object storage, with a concrete AWS S3 implementation. Built for NYU OSPSD Spring '26.

---

## What This Project Does

Working with AWS S3 directly means dealing with `boto3`, regions, credentials, multipart uploads, and AWS-specific types — everywhere in your code. This project hides all of that behind a simple, stable interface.

You write code against `CloudStorageClient`. You never import `boto3`. When you need the local S3 implementation, you call `get_client_impl()` from `aws_client_impl`. When you need the remote HTTP-backed implementation, you call `get_client_impl()` from `aws_client_adapter`. In both cases, the consumer code stays the same.

```python
from aws_client_impl.s3_client import get_client_impl

client = get_client_impl()                                 # returns CloudStorageClient
files = client.list_files("my-bucket", "")               # list all objects in a container
client.upload_file("my-bucket", "local/data.csv", "data.csv")
client.download_file("my-bucket", "data.csv", "local/copy.csv")
```

## Architecture

The project is a [`uv` workspace](https://docs.astral.sh/uv/concepts/workspaces/) with four installable packages plus an external interface dependency:

```
ospsd-team-2/
├── src/
│   ├── aws_client_impl/            # The concrete AWS S3 implementation
│   │   └── aws_client_impl/
│   │       └── s3_client.py        # S3Client — implements CloudStorageClient via boto3
│   ├── aws_client_service/         # FastAPI HTTP service — wraps aws_client_impl
│   │   └── aws_client_service/
│   │       └── main.py             # GET /health, GET /files, POST /files/..., GET /download, DELETE /files/...
│   ├── aws_s3_cloud_storage_service_client/  # Autogenerated OpenAPI client
│   └── aws_client_adapter/         # Adapter implementing CloudStorageClient over HTTP
├── tests/
│   ├── integration/                # Tests that verify wiring works end-to-end
│   └── e2e/                        # Full workflow tests against real AWS infrastructure
├── main.py                         # Example entry point demonstrating the full flow
├── pyproject.toml                  # Workspace root — all tool config lives here
└── docs/                           # Sphinx documentation source
```

The abstract contract (`CloudStorageClient`, domain exceptions, `ObjectInfo`, `DeleteResult`) comes from the external `cloud_storage_api` package, installed via git dependency.

### How Client Wiring Works

The interface (`cloud_storage_api`) is an external package with **zero knowledge** of AWS or boto3. It only defines `CloudStorageClient`, domain types, and exceptions.

Each implementation package provides a `get_client_impl()` factory:

```python
from aws_client_impl.s3_client import get_client_impl

client = get_client_impl()  # returns a fully configured S3Client
```

```
┌──────────────────────────┐        ┌──────────────────────────┐
│  cloud_storage_api (ext) │        │    aws_client_impl        │
│  ──────────────────────  │        │  ───────────────────────  │
│  CloudStorageClient (ABC)│◄───────│  S3Client                 │
│  ObjectInfo, DeleteResult│        │  get_client_impl()        │
│  domain exceptions       │        │                           │
└──────────────────────────┘        └──────────────────────────┘
         ▲
         │  callers only ever touch this side
```

## AWS Credentials

The local S3 implementation reads credentials from environment variables. **Never hardcode secrets.**

```shell
export AWS_ACCESS_KEY_ID="your_access_key_id"
export AWS_SECRET_ACCESS_KEY="your_secret_access_key"
export AWS_REGION="us-east-1"
export AWS_BUCKET_NAME="your-bucket-name"   # used by main.py demo only
```

You can put these in a local `.env` file — it is listed in `.gitignore` and will never be committed.

> **Tip:** You only need credentials to run `main.py` or the E2E tests against real S3. Unit and integration tests mock all AWS calls and work without credentials.

> **Note:** CI never uses long-lived access keys. The CircleCI pipeline authenticates via OIDC and assumes an IAM role directly. See [CONTRIBUTING.md](CONTRIBUTING.md#cicd) for setup instructions.

## Running the Application

**CLI example** — with credentials set:

```shell
uv run python main.py
```

This creates a client, lists files in `AWS_BUCKET_NAME`, and prints them.

**FastAPI service** — starts the HTTP server on port 8000:

```shell
export API_KEY="replace-me"
uv run uvicorn aws_client_service.main:app --reload
```

Protected file endpoints accept either the browser-based GitHub OAuth session or an API key via `X-API-Key` / `Authorization: Bearer`.

Beginner walkthrough: `https://ospsd-team-2.fly.dev/guide/curl-tutorial.html`

Upload an object:

```shell
curl -X POST "http://localhost:8000/files/my-bucket/data.csv" \
  -H "X-API-Key: $API_KEY" \
  -F "file=@/path/to/local/data.csv"
```

Then download a file:

```shell
curl -H "X-API-Key: $API_KEY" \
  "http://localhost:8000/download?container=my-bucket&object_name=data.csv" \
  --output data.csv
```

Delete an object:

```shell
curl -X DELETE \
  -H "X-API-Key: $API_KEY" \
  "http://localhost:8000/files/my-bucket/data.csv"
```

List matching objects:

```shell
curl -H "X-API-Key: $API_KEY" "http://localhost:8000/files?container=my-bucket&prefix=data"
```

### Remote Adapter

To consume the deployed service through the original `CloudStorageClient`
interface, use the adapter package:

```python
from aws_client_adapter import get_client_impl

client = get_client_impl()
files = client.list_files("my-bucket", "reports/")
```

Set `CLOUD_STORAGE_SERVICE_BASE_URL` to the service base URL and `API_KEY` to a
valid token.

### Curl Smoke Test

For a fully local curl workflow without AWS credentials, run the service with the filesystem-backed test override:

```shell
uv run python scripts/run_curl_test_service.py
```

That script seeds a local API key of `local-curl-test-key` and uses `scripts/curl-dummy.txt` as the upload fixture.

```shell
curl http://127.0.0.1:8001/health
curl http://127.0.0.1:8001/
curl -D - -o /dev/null http://127.0.0.1:8001/auth/login
curl "http://127.0.0.1:8001/auth/callback?code=dummy&state=dummy"
curl -H "X-API-Key: local-curl-test-key" -F "file=@scripts/curl-dummy.txt" \
  "http://127.0.0.1:8001/files/demo/scripts/curl-dummy.txt"
curl -H "X-API-Key: local-curl-test-key" \
  "http://127.0.0.1:8001/files?prefix=scripts/"
curl -H "X-API-Key: local-curl-test-key" \
  "http://127.0.0.1:8001/download?bucket_name=demo&object_name=scripts/curl-dummy.txt" \

curl -X DELETE -H "X-API-Key: local-curl-test-key" \
  "http://127.0.0.1:8001/files/demo/scripts/curl-dummy.txt"
```

## Deployment

This service is packaged as a single container image and configured for Fly.io deployment.

- Platform: `Fly.io`
- Configured public base URL: `https://ospsd-team-2.fly.dev`
- OpenAPI schema: `https://ospsd-team-2.fly.dev/openapi.json`
- Health endpoint: `https://ospsd-team-2.fly.dev/health`
- Published Sphinx docs: `https://ospsd-team-2.fly.dev/guide/`

The generated client can talk to the deployed service directly:

```python
from aws_s3_cloud_storage_service_client import Client

client = Client(base_url="https://ospsd-team-2.fly.dev")
```

For protected endpoints, use the generated authenticated client with the same
`API_KEY` that you configure in Fly:

```python
from aws_s3_cloud_storage_service_client import AuthenticatedClient

client = AuthenticatedClient(
    base_url="https://ospsd-team-2.fly.dev",
    token="your-api-key",
)
```

To regenerate the client from the deployed schema:

```shell
uvx openapi-python-client generate \
  --url https://ospsd-team-2.fly.dev/openapi.json
```

### Runtime Configuration

Store all runtime values in Fly secrets or CircleCI contexts. Do not commit secrets to source control.

| Variable | Purpose | Example deployment value |
|---|---|---|
| `SESSION_SECRET_KEY` | Signs Starlette session cookies | random 32+ byte string |
| `API_KEY` | Non-browser auth for curl and generated clients | random 32+ byte string |
| `AWS_ACCESS_KEY_ID` | AWS access key for the deployed S3 implementation | `AKIA...` |
| `AWS_SECRET_ACCESS_KEY` | AWS secret for the deployed S3 implementation | secret value |
| `AWS_REGION` | AWS region for S3 operations | `us-east-1` |
| `AWS_BUCKET_NAME` | Bucket used by the local `main.py` demo | `ospsd-team-2-prod` |
| `CLOUD_STORAGE_SERVICE_BASE_URL` | Base URL used by `aws_client_adapter` | `https://ospsd-team-2.fly.dev` |
| `GITHUB_CLIENT_ID` | GitHub OAuth app client id | GitHub app id |
| `GITHUB_CLIENT_SECRET` | GitHub OAuth app client secret | GitHub app secret |
| `GITHUB_AUTH_URI` | GitHub authorization endpoint | `https://github.com/login/oauth/authorize` |
| `GITHUB_TOKEN_URI` | GitHub token endpoint | `https://github.com/login/oauth/access_token` |
| `GITHUB_LOCAL_REDIRECT_URI` | OAuth callback URL used by the service | `https://ospsd-team-2.fly.dev/auth/callback` |

`PORT` is set in `fly.toml`, so it is not stored as a secret.

### Fly.io Steps

1. Install the CLI and authenticate.

```shell
brew install flyctl
fly auth login
```

2. Create the Fly app from the repository root if it does not exist yet.

```shell
fly launch --copy-config --name ospsd-team-2
```

3. Store runtime secrets in Fly, not in git.

```shell
fly secrets set \
  SESSION_SECRET_KEY="..." \
  API_KEY="..." \
  AWS_ACCESS_KEY_ID="..." \
  AWS_SECRET_ACCESS_KEY="..." \
  AWS_REGION="us-east-1" \
  AWS_BUCKET_NAME="..." \
  CLOUD_STORAGE_SERVICE_BASE_URL="https://ospsd-team-2.fly.dev" \
  GITHUB_CLIENT_ID="..." \
  GITHUB_CLIENT_SECRET="..." \
  GITHUB_AUTH_URI="https://github.com/login/oauth/authorize" \
  GITHUB_TOKEN_URI="https://github.com/login/oauth/access_token" \
  GITHUB_LOCAL_REDIRECT_URI="https://ospsd-team-2.fly.dev/auth/callback"
```

4. Deploy the container.

```shell
fly deploy
```

5. Verify the public deployment.

```shell
curl https://ospsd-team-2.fly.dev/health
curl https://ospsd-team-2.fly.dev/openapi.json
```

`fly.toml` configures Fly to probe `/health` for operational checks.

### CircleCI Pipeline

The repository deploys through CircleCI in `.circleci/config.yml`.

- Workflow order: `lint` -> `unit-tests` -> `integration-tests` -> `e2e-tests` -> `deploy-fly`
- `deploy-fly` runs only for pushes to the `hw-2` branch
- `deploy-fly` uses the `flyio` CircleCI context and expects `FLY_API_TOKEN`
- `e2e-tests` uses the `aws-ospsd` CircleCI context for AWS credentials
- Application secrets stay in Fly via `fly secrets`, not in CircleCI or git
