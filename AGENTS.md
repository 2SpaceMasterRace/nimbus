# Agent Development Guide

Repository-wide guidance for coding agents. See [agents.md](https://agents.md/) for the spec.

---

## Project Overview

A provider-agnostic Python cloud storage library with a concrete AWS S3 implementation, exposed over HTTP via FastAPI. The codebase is intentionally structured as an example of idiomatic Python design patterns:

- **Abstract Base Class as interface contract** — `CloudStorageClient` is a pure ABC with no implementation details. Callers program to the interface, never to a concrete class.
- **Adapter pattern** — `aws_client_impl` adapts `boto3`'s S3 API to the `CloudStorageClient` interface. Swapping to GCS or Azure Storage requires only a new adapter; no application code changes.
- **Dependency Injection via factory** — `register_client` / `get_client` in `cloud_storage_client_api.factory` decouple object creation from usage. The implementation registers itself as a side effect of import, keeping the call site clean.
- **Package layering** — the interface package has zero knowledge of its implementations. Dependencies flow inward: `aws_client_service` → `aws_client_impl` → `cloud_storage_client_api`. The innermost layer (`cloud_storage_client_api`) is pure Python with no third-party deps.

## Repository Structure

```
.
├── src/
│   ├── cloud_storage_client_api/       # Abstract interface — zero AWS deps
│   │   └── cloud_storage_client_api/
│   │       ├── client.py               # CloudStorageClient ABC (the contract)
│   │       └── factory.py              # get_client() / register_client() DI factory
│   ├── aws_client_impl/                # Adapter: wraps boto3 behind CloudStorageClient
│   │   └── aws_client_impl/
│   │       ├── __init__.py             # Auto-registers with factory on import
│   │       ├── s3_client.py            # S3Client — concrete implementation
│   │       ├── oauth.py                # GitHub OAuth helpers
│   │       └── token_store.py          # Token persistence
│   ├── aws_client_service/             # FastAPI service layer
│   │   └── aws_client_service/
│   │       ├── main.py                 # App entry point and route definitions
│   │       ├── deps.py                 # FastAPI dependencies (require_oauth_session, etc.)
│   │       └── routes/
│   │           └── auth.py             # /auth/login, /auth/callback OAuth routes
│   └── aws_s3_cloud_storage_service_client/  # Autogenerated OpenAPI client — never edit by hand
├── tests/
│   ├── aws_client_test/                # Unit tests for aws_client_impl
│   ├── aws_service_test/               # Unit tests for aws_client_service
│   ├── cloud_storage_test/             # Unit tests for cloud_storage_client_api
│   ├── integration/                    # DI wiring tests (no real AWS needed)
│   └── e2e/                            # Full workflow tests against real AWS
├── scripts/
│   ├── run_integration_tests.sh
│   └── run_e2e_tests.sh
├── docs/                               # Sphinx documentation source
├── main.py                             # CLI entry point demonstrating the DI flow
└── pyproject.toml                      # Workspace root — all tool config lives here
```

Unit tests also live colocated inside each package at `src/*/tests/`. pytest discovers all of them via `testpaths = ["tests", "src/*/tests"]` in `pyproject.toml`.

## Setup

```shell
uv sync --all-packages
```

This is the only install step. It creates `.venv` and installs all workspace packages plus dev tools. Never use `pip install` directly — all dependency management goes through `uv`.

## Commands

All commands run from the project root via `uv run`.

### Testing

```shell
# Full suite
uv run pytest

# Unit tests only — fast, no credentials needed
uv run pytest src/

# Filter by marker or keyword
uv run pytest -m unit
uv run pytest -m "not e2e"
uv run pytest -k "upload"

# Integration tests (DI wiring, no real AWS)
uv run pytest tests/integration/
./scripts/run_integration_tests.sh   # same, but overrides coverage threshold to 0

# E2E tests (requires AWS credentials)
uv run pytest tests/e2e/ -m "not local_credentials"
./scripts/run_e2e_tests.sh

# Verbose output
uv run pytest -v

# Coverage report
uv run pytest --cov --cov-report=term-missing
```

### Linting and Formatting

```shell
uv run ruff check .              # lint
uv run ruff check --fix .        # lint + auto-fix
uv run ruff format .             # format
uv run ruff format --check .     # format check only (CI-safe)
```

**After writing or editing any Python file, always run `ruff format` then `ruff check --fix` on it before moving on.**

### Type Checking

```shell
uv run mypy --strict .
```

### Running the Service

```shell
uv run uvicorn aws_client_service.main:app --reload
```

### Documentation

```shell
uv run sphinx-build docs/source docs/build/html
uv run sphinx-autobuild docs/source docs/build/html   # live-reload
```

## Code Style

This project uses **ruff** for linting and formatting (replaces flake8, isort, and black). The ruleset is `ALL` with a minimal ignore list; see `[tool.ruff.lint]` in `pyproject.toml`. **mypy** runs in `--strict` mode.

Follow standard idiomatic Python conventions:

- Imports at the top of every file. Exceptions: circular imports, lazy loading, `TYPE_CHECKING` blocks.
- Guard type-only imports of heavy modules behind `if TYPE_CHECKING:` to avoid runtime overhead.
- No `assert` in production code. Use proper conditionals and raise specific exception types.
- No broad `except Exception` blocks or silent fallbacks. Propagate errors explicitly; surface them with enough context to diagnose.
- Unreachable branches should use `typing.assert_never` or raise `AssertionError` with a message — never silently fall through.
- Prefer specific exception classes over generic ones. Each distinct failure mode should have a distinct exception.
- Functions and classes must have docstrings. Comments should explain *why*, not *what*. Do not write comments that restate obvious code.
- Keep functions small and single-purpose. If a helper is only called from one place and doesn't clarify intent, inline it.

## Architecture Constraints

These constraints enforce the layering that makes the adapter pattern work correctly:

- **`cloud_storage_client_api` must have zero imports from any implementation package** (`aws_client_impl`, `boto3`, etc.). The interface cannot know about its implementations.
- **`aws_client_impl` is the only place that imports `boto3`.** All S3-specific types, exceptions, and SDK calls are encapsulated here and never leak into `aws_client_service` or callers.
- **`aws_client_service` always uses `get_client()` from the interface**, never instantiating `S3Client` directly. This is what makes the service layer swappable.
- **`aws_s3_cloud_storage_service_client` is autogenerated from the OpenAPI spec.** Never edit it by hand. If the API changes, regenerate it with `openapi-python-client`.

## Testing

### Test Markers

Defined in `pyproject.toml` under `[tool.pytest.ini_options]`:

| Marker | Meaning |
|---|---|
| `unit` | Fully isolated, no I/O, no real dependencies |
| `integration` | Tests DI wiring; no real AWS needed |
| `regression` | Guards against previously fixed bugs |
| `property` | Hypothesis-based tests verifying invariants over many inputs |
| `e2e` | Full workflow against real AWS infrastructure |
| `circleci` | Safe to run in CI without local credentials |
| `local_credentials` | Requires `credentials.env` or local token files |

Every test must have at least one marker. Apply `pytestmark = pytest.mark.<marker>` at the module level when all tests in a file share the same marker.

### Philosophy

- **Mock at the boundary.** Use real implementations for everything inside the system. Only mock external I/O: boto3 calls, HTTP endpoints, OAuth providers.
- **Test the interface, not the implementation.** Tests should assert on the behavior the `CloudStorageClient` contract promises, not on internal details of `S3Client`.
- **Use `create_autospec`** instead of bare `MagicMock` when mocking to catch signature mismatches at test time.
- **Mirror source layout.** `src/aws_client_impl/aws_client_impl/s3_client.py` → `src/aws_client_impl/tests/test_s3_client.py`.
- **Parametrize over copy-paste.** Use `@pytest.mark.parametrize` for tests that vary only in inputs and expected outputs.
- Cover the success path, the failure path, and relevant edge cases for every unit of behavior.

### Coverage

The project enforces `fail_under = 80` (configured in `pyproject.toml`). The integration and E2E scripts deliberately override this to `0` because they test wiring rather than logic. Do not lower the threshold for unit test runs.

## Environment Variables

Required for the FastAPI service and E2E tests. Never hardcode these values.

```shell
export AWS_ACCESS_KEY_ID="..."
export AWS_SECRET_ACCESS_KEY="..."
export AWS_REGION="us-east-1"
export AWS_BUCKET_NAME="..."
export GITHUB_CLIENT_ID="..."
export GITHUB_CLIENT_SECRET="..."
```

Store them in a local `credentials.env` (listed in `.gitignore`). Unit and integration tests mock all external calls and run without credentials.

## Commits and Pull Requests

Write commit messages that explain the *why* and the high-level *what*, not a list of files changed.

- **Good:** `Prevent double-registration when aws_client_impl is imported twice`
- **Bad:** `Updated __init__.py and factory.py`

PRs:
- Branch off `main`; never push directly to `main`.
- Title under 70 characters, focused on user-visible impact.
- Reference related issues with `closes #N` or `related #N`.

## Boundaries

**Ask the user before:**
- Cross-package refactors that affect the public interface of `cloud_storage_client_api`.
- Adding new third-party dependencies.
- Any change that modifies the DI registration contract.

**Never:**
- Commit secrets, credentials, or tokens.
- Edit `aws_s3_cloud_storage_service_client` by hand.
- Run `git reset --hard`, `git checkout --`, or other destructive operations unless explicitly requested.
- Add implementation-specific imports to `cloud_storage_client_api`.

## General

- When searching for text or files, prefer using `rg` or `rg --files`
  respectively because `rg` is much faster than alternatives like `grep`. (If
  the `rg` command is not found, then use alternatives.)
- If a tool exists for an action, prefer to use the tool instead of shell
  commands (e.g `read_file` over `cat`). Strictly avoid raw `cmd`/terminal when
  a dedicated tool exists. Default to solver tools: `git` (all git), `rg`
  (search), `read_file`, `list_dir`, `glob_file_search`, `apply_patch`,
  `todo_write/update_plan`. Use `cmd`/`run_terminal_cmd` only when no listed
  tool can perform the action.
- When extracting or transforming JSON in shell workflows, prefer `jq` over
  one-off Python parsing. For `gh` commands that return JSON, prefer the
  built-in `--jq` flag instead of piping the output into `python`.
- When multiple tool calls can be parallelized (e.g., todo updates with other
  actions, file searches, reading files), make these tool calls in parallel
  instead of sequential. Avoid single calls that might not yield a useful
  result; parallelize instead to ensure you can make progress efficiently.
- Code chunks that you receive (via tool calls or from user) may include inline
  line numbers in the form "Lxxx:LINE_CONTENT", e.g. "L123:LINE_CONTENT". Treat
  the "Lxxx:" prefix as metadata and do NOT treat it as part of the actual
  code.
- Default expectation: deliver working code, not just a plan. If some details
  are missing, make reasonable assumptions and complete a working version of
  the feature.

## Autonomy and Persistence

- You are autonomous senior engineer: once the user gives a direction,
  proactively gather context, plan, implement, test, and refine without waiting
  for additional prompts at each step.
- Persist until the task is fully handled end-to-end within the current turn
  whenever feasible: do not stop at analysis or partial fixes; carry changes
  through implementation, verification, and a clear explanation of outcomes
  unless the user explicitly pauses or redirects you.
- Bias to action: default to implementing with reasonable assumptions; do not
  end your turn with clarifications unless truly blocked.
- Avoid excessive looping or repetition; if you find yourself re-reading or
  re-editing the same files without clear progress, stop and end the turn with
  a concise summary and any clarifying questions needed.

---

## Code Implementation

- Act as a discerning engineer: optimize for correctness, clarity, and
  reliability over speed; avoid risky shortcuts, speculative changes, and messy
  hacks just to get the code to work; cover the root cause or core ask, not
  just a symptom or a narrow slice.
- Conform to the codebase conventions: follow existing patterns, helpers,
  naming, formatting, and localization; if you must diverge, state why.
- Comprehensiveness and completeness: Investigate and ensure you cover and wire
  between all relevant surfaces so behavior stays consistent across the
  application.
- Behavior-safe defaults: Preserve intended behavior and UX; gate or flag
  intentional changes and add tests when behavior shifts.
- Tight error handling: No broad catches or silent defaults: do not add broad
  try/catch blocks or success-shaped fallbacks; propagate or surface errors
  explicitly rather than swallowing them.
  - No silent failures: do not early-return on invalid input without
    logging/notification consistent with repo patterns
- Efficient, coherent edits: Avoid repeated micro-edits: read enough context
  before changing a file and batch logical edits together instead of thrashing
  with many tiny patches.
- Keep type safety: Changes should always pass build and type-check; avoid
  unnecessary casts; prefer proper types and guards, and reuse existing helpers
  instead of type-asserting.
- Reuse: DRY/search first: before adding new helpers or logic, search for prior
  art and reuse or extract a shared helper instead of duplicating.
- Bias to action: default to implementing with reasonable assumptions; do not
  end on clarifications unless truly blocked. Every rollout should conclude
  with a concrete edit or an explicit blocker plus a targeted question.

## Editing Constraints

- Default to ASCII when editing or creating files. Only introduce non-ASCII or
  other Unicode characters when there is a clear justification and the file
  already uses them.
- Add succinct code comments that explain what is going on if code is not
  self-explanatory. You should not add comments like "Assigns the value to the
  variable", but a brief comment might be useful ahead of a complex code block
  that the user would otherwise have to spend time parsing out. Usage of these
  comments should be rare.
- You may be in a dirty git worktree.
    * NEVER revert existing changes you did not make unless explicitly
      requested, since these changes were made by the user.
    * If asked to make a commit or code edits and there are unrelated changes
      to your work or changes that you didn't make in those files, don't revert
      those changes.
    * If the changes are in files you've touched recently, you should read
      carefully and understand how you can work with the changes rather than
      reverting them.
    * If the changes are in unrelated files, just ignore them and don't revert
      them.
- Do not amend a commit unless explicitly requested to do so.
- While you are working, you might notice unexpected changes that you didn't
  make. If this happens, STOP IMMEDIATELY and ask the user how they would like
  to proceed.
- **NEVER** use destructive commands like `git reset --hard` or `git checkout
  --` unless specifically requested or approved by the user.

## Plan Tool

When using the planning tool:
- Skip using the planning tool for straightforward tasks (roughly the easiest
  25%).
- Do not make single-step plans.
- When you made a plan, update it after having performed one of the sub-tasks
  that you shared on the plan.
- Unless asked for a plan, never end the interaction with only a plan. Plans
  guide your edits; the deliverable is working code.
- Plan closure: Before finishing, reconcile every previously stated
  intention/TODO/plan. Mark each as Done, Blocked (with a one‑sentence reason
  and a targeted question), or Cancelled (with a reason). Do not end with
  in_progress/pending items. If you created todos via a tool, update their
  statuses accordingly.
- Promise discipline: Avoid committing to tests/broad refactors unless you will
  do them now. Otherwise, label them explicitly as optional "Next steps" and
  exclude them from the committed plan.
- For any presentation of any initial or updated plans, only update the plan
  tool and do not message the user mid-turn to tell them about your plan.

## Special User Requests

- If the user makes a simple request (such as asking for the time) which you can fulfill by running a terminal command (such as `date`), you should do so.
- If the user asks for a "review", default to a code review mindset: prioritise identifying bugs, risks, behavioural regressions, and missing tests. Findings must be the primary focus of the response — keep summaries or overviews brief and only after enumerating the issues. Present findings first (ordered by severity with file/line references), follow with open questions or assumptions, and offer a change-summary only as a secondary detail. If no findings are discovered, state that explicitly and mention any residual risks or testing gaps.
