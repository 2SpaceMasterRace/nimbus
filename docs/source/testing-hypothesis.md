# Property-Based Testing With Hypothesis

Most beginner tests use examples chosen by a human.

```python
def test_uppercase_returns_uppercase_text() -> None:
    assert "hello".upper() == "HELLO"
```

That is an example-based test.

Property-based testing asks a different question:

> What should always be true for a whole class of inputs?

Hypothesis is the Python library we use for property-based tests.

## Example tests versus properties

Example test:

```python
def test_reverse_example() -> None:
    assert list(reversed([1, 2, 3])) == [3, 2, 1]
```

Property test:

```python
from hypothesis import given
from hypothesis import strategies as st


@given(st.lists(st.integers()))
def test_reversing_twice_returns_original(values: list[int]) -> None:
    assert list(reversed(list(reversed(values)))) == values
```

Hypothesis generates many lists:

```text
[]
[0]
[1, -1, 500]
[42, 42, 42]
[-999999999, 0, 999999999]
...
```

For every generated list, reversing twice should return the original list.

```text
Strategy: lists of integers
          |
          v
Generated examples
          |
          v
Run the test for each example
          |
          v
If a failure appears, shrink it to the simplest failing case
```

## What @given means

```python
@given(st.text())
def test_never_crashes(value: str) -> None:
    value.encode("utf-8")
```

`@given(st.text())` means:

- generate a string,
- pass it into the test as `value`,
- run the test many times with different strings.

`st` stands for strategies. A strategy describes the kind of data Hypothesis
should generate.

Common strategies:

```python
st.integers()
st.text()
st.booleans()
st.lists(st.integers())
st.dictionaries(st.text(), st.integers())
st.one_of(st.none(), st.text())
```

## Hypothesis finds weird inputs

Humans often test normal-looking values:

```python
"hello"
"docs/report.txt"
"user-123"
```

Hypothesis will try values like:

```python
""
"\x00"
"../../etc/passwd"
"🔥"
"a" * 300
```

That is exactly why it is useful for validation, serialization, IDs, signatures,
and boundary code.

## Shrinking: the best part

Suppose we accidentally write:

```python
def buggy_sort(values: list[int]) -> list[int]:
    if len(values) == 3:
        return values
    return sorted(values)
```

Property:

```python
@given(st.lists(st.integers()))
def test_buggy_sort_returns_sorted_values(values: list[int]) -> None:
    result = buggy_sort(values)

    assert result == sorted(values)
```

Hypothesis may find a huge failing list first. Then it shrinks the failure to a
small example:

```text
Falsifying example: test_buggy_sort_returns_sorted_values(
    values=[0, 1, 0],
)
```

That small example is easier to debug.

## A repository-style property: session IDs

Session IDs are security-sensitive because they become filenames. We need to
know they cannot escape the session directory.

Example property:

```python
from hypothesis import given
from hypothesis import strategies as st

SAFE_ALPHABET = "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789-_:."


@given(st.text(alphabet=SAFE_ALPHABET, min_size=1, max_size=300))
def test_valid_session_id_file_stem_is_deterministic(session_id: str) -> None:
    first = _session_file_stem(session_id)
    second = _session_file_stem(session_id)

    assert first == second
    assert "/" not in first
    assert "\\" not in first
```

This checks many valid session IDs. For each one:

- filename derivation is deterministic,
- the derived stem has no Unix path separator,
- the derived stem has no Windows path separator.

Output:

```text
.                                                                        [100%]
1 passed in 0.34s
```

Property tests are often slower than normal unit tests because they run many
examples. That is expected.

## A repository-style property: signing

Signed requests should be sensitive to the body. If the body changes, the
signature should no longer verify.

```python
@given(
    body=st.binary(min_size=0, max_size=512),
    tampered_body=st.binary(min_size=0, max_size=512),
)
def test_signature_rejects_tampered_body(body: bytes, tampered_body: bytes) -> None:
    assume(tampered_body != body)

    headers = sign_request(
        body=body,
        secret="test-secret",
        timestamp="1713840000",
        nonce="nonce-123",
    )

    with pytest.raises(AuthenticationError):
        verify_request(
            body=tampered_body,
            headers=headers,
            secret="test-secret",
        )
```

`assume(tampered_body != body)` tells Hypothesis to skip cases where the two
generated byte strings are identical.

## Use per-example filesystem isolation

Important repo rule:

> Use `tempfile.TemporaryDirectory()` inside a Hypothesis test that writes to
> disk.

Do not use `tmp_path` for per-example filesystem state inside one Hypothesis
test. `tmp_path` is created once for the whole test function, while Hypothesis
runs many examples inside that one function.

Good:

```python
from tempfile import TemporaryDirectory
from pathlib import Path


@given(st.text(alphabet=SAFE_ALPHABET, min_size=1, max_size=100))
def test_session_round_trips(session_id: str) -> None:
    with TemporaryDirectory() as tmp:
        session_dir = Path(tmp)

        save_session(session_dir, session_id, {"messages": []})
        loaded = load_session(session_dir, session_id)

        assert loaded["session_id"] == session_id
```

Why this matters:

- Hypothesis may run 100 examples.
- Each example needs clean filesystem state.
- Shared files can contaminate later examples.

## When to use Hypothesis

Use Hypothesis when:

- the input space is large,
- the behavior is an invariant,
- examples feel arbitrary,
- validation is security-sensitive,
- serialization must round-trip,
- arithmetic must stay within bounds,
- or state transitions must preserve safety.

Good Hypothesis targets in this repo:

- session ID validation,
- HMAC signing,
- token-bucket arithmetic,
- conversation trimming,
- runtime action and approval transitions,
- ACL-filtered search projections,
- protocol event and error presentation decoding,
- request model validation,
- JSON deserialization,
- bounded history invariants.

## When not to use Hypothesis

Do not use Hypothesis for every test.

Avoid it when:

- one obvious example proves the behavior,
- the setup is expensive,
- the expected result is hard to define,
- or the generated data does not match a real contract.

This is better as a normal unit test:

```python
def test_delete_file_maps_not_found_to_domain_exception() -> None:
    ...
```

The important case is a specific `404` response. We do not need generated data.

## The Hypothesis mindset

Ask:

> What must always be true?

Then make that statement executable.

Examples:

- Saving and loading a valid session preserves the logical session ID.
- Signing and verifying the same payload succeeds.
- Changing the signed body fails verification.
- A token bucket never stores more tokens than capacity.
- Conversation trimming never leaves an orphan tool result.
- A stale action transition does not mutate the action or append an event.
- A wrong actor, wrong tenant, expired approval, or changed target fails closed.
- Search results are always a subset of tenant and ACL-visible documents.

Property tests are not magic. They are just tests where the examples come from a
generator instead of your fingers.

## Stateful testing

Some behavior is not about one input. It is about a sequence of actions.

Conversation history is a good example:

```text
add user message
add assistant message
add tool result
trim history
serialize
deserialize
```

One example cannot cover all interesting orders. Hypothesis has stateful testing
for this.

Simplified shape:

```python
from hypothesis.stateful import RuleBasedStateMachine, invariant, rule


class ConversationMachine(RuleBasedStateMachine):
    def __init__(self) -> None:
        super().__init__()
        self.conversation = Conversation(system="sys")

    @rule(text=st.text(max_size=50))
    def add_user_message(self, text: str) -> None:
        self.conversation.add_user(text)

    @rule(text=st.text(max_size=50))
    def add_assistant_message(self, text: str) -> None:
        self.conversation.add_assistant(text)

    @invariant()
    def system_prompt_is_never_lost(self) -> None:
        assert self.conversation.messages()[0].role is Role.SYSTEM


TestConversationMachine = ConversationMachine.TestCase
```

Hypothesis generates action sequences and checks the invariant after steps.

Use stateful testing when:

- correctness depends on operation order,
- rollback matters,
- trimming or cleanup happens over time,
- or a bug might only appear after several actions.

Do not start with stateful testing. Start with examples. Add stateful tests when
you can clearly name the invariant.

## Runtime property tests

Runtime property tests should protect safety contracts, not implementation
accidents. The useful shape is:

```text
generate a small valid runtime state
apply one generated operation or operation sequence
assert the safety invariant and public store behavior
```

Current examples live in
`src/nimbus_runtime/tests/test_runtime_properties.py` and
`src/nimbus_runtime/tests/test_store_properties.py`. They cover:

- action transition validation versus the transition oracle;
- compare-and-set action transitions;
- once-per-idempotency-key action creation;
- approval decisions bound to actor, tenant, expiry, and exact target;
- ACL-aware search results after tenant filtering;
- search re-indexing that replaces stale chunks instead of appending them;
- worker lease exclusion, expiry, and heartbeat ownership;
- artifact digest immutability, tenant scoping, and chronological session listing.

Keep these tests bounded. SQLite-backed examples are more expensive than pure
function properties, so prefer short safe IDs, fixed timestamps, small document
sets, and explicit `max_examples` settings. Use `tempfile.TemporaryDirectory()`
inside each Hypothesis test that writes to a file-backed store so one generated
example cannot contaminate another.

## Adapter boundary property tests

Adapters are good property-test targets when they parse generated-client output
or translate service failures into domain exceptions. The invariant should be
about the boundary contract, not a private implementation accident:

- list responses map every service object and return deterministic ordering;
- optional generated-client fields preserve `None` versus provided values;
- malformed or surprising error bodies still become stable domain messages;
- HTTP status and detail classify errors without leaking raw transport shapes.

The current examples live in
`src/aws_client_adapter/tests/test_service_adapter_properties.py`. Keep generated
payloads small and patch the generated-client call inside the property body so
each Hypothesis example owns its own boundary response.
